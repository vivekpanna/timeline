# Timeline Product Discovery

Use this skill to turn product references into a testable product brief for an original timeline tool. Treat reference products as evidence about user needs, not as implementation or visual specifications to copy.

## Establish the evidence boundary

1. Identify the exact target URL, audience, intended users, and requested level of similarity.
2. Start with public product pages, documentation, help articles, and user-provided observations. Use an authenticated editor only when the user has legitimate access and explicitly makes that session available.
3. Do not bypass authentication, access controls, paywalls, or technical restrictions. Do not extract private data, secrets, or source code that is not intentionally public.
4. Keep a short evidence ledger with `Observed`, `Inferred`, `Unknown`, and `Product choice` entries. Link each observation to its source and date. A marketing claim is not proof that a feature behaves a particular way.
5. If the editor is inaccessible, state the limit and continue from public evidence. Do not invent hidden screens, interactions, or plan restrictions.

## Define the user outcome

Write one sentence for the primary job, then identify:

- The user and audience for the output.
- The input data they already have.
- The artifact they need to create, update, or share.
- The shortest successful workflow and its completion signal.
- The constraints that shape the MVP: free access, browser support, privacy, import/export, and whether an account is acceptable.

For an Office Timeline-like reference, public materials support these candidate needs: create executive-ready timeline visuals, roadmap and swimlane views, update project status, share a current plan, and export presentation-ready output. Confirm each against the user's goals before treating it as a requirement. The live editor may require sign-in; authenticated behavior remains unknown unless observed legitimately.

## Prioritize the free MVP

Prefer a complete solo workflow before team features:

1. Create a timeline from a blank state or sample.
2. Add, edit, reorder, and remove tasks, milestones, and groups/swimlanes.
3. Set dates, labels, progress/status, and visual style.
4. Inspect the result at useful zoom levels and keep labels legible.
5. Save and reopen locally; provide dependable export to a common image/document format.

Treat account sharing, roles, live collaboration, connected integrations, template catalogs, and native PowerPoint as optional follow-on scope. Promote any of these only when required by the user and feasible within the free-product constraint. A free feature set must not depend on a paid service or a trial that silently expires.

## Produce a usable brief

Record problem statement, primary persona, MVP scope, explicit exclusions, requirements, acceptance checks, unresolved questions, and evidence links. Phrase acceptance checks as observable outcomes. Separate compatibility goals (similar user outcome) from non-goals (brand, copied screen layout, wording, templates, icons, code, or assets).

End by naming the next decision or handoff. Do not start implementation when the user asked only for research or a brief.
